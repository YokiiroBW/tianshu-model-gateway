# TS-043：用量与延迟诊断的取舍

2026-09-16。本切片在既有持久回执之上加一段只读聚合：两个显式身份鉴权的读端口和一个只读本地 CLI。它不发布新业务数据、不新增模型协议、不改根合同、不估费用、不做后台遥测。

## 为什么用私有表而不是扩既有回执合同

能由既有回执推导的数据一律派生：身份、`reason`、上游 HTTP 状态、`elapsed_ms`、归一化 `usage`/`usage_complete` 都从 `requests`/`native_requests` 读，私有表只放**无法从既有结构索引**的新性能事实：完成墙钟毫秒（用于时间窗口与排序）、三个单调计时（首个上游字节、首个事件、首个输出）、用量来源枚举、归一化 token 数与完整性。

理由：既有回执是已发布消费者（平台侧回执读取、发布方 `validate.py` 关系检查）的稳定接口，加字段会改变合同；而逐次延迟需要按时间窗口索引排序，回执 JSON 里做不到。因此新事实写本产品私有表 `request_metrics`/`native_request_metrics`，键与回执主键一致（Chat 为 service+request_id，native 为 contract/principal/caller/namespace+request_id），`INSERT OR REPLACE` 保证重复终态只留一行、不双计。

## 为什么不复制内容、不聚合供应商原始 usage

私有表只存标量与枚举：没有消息正文、工具参数、Key、私有 URL、异常文本，也没有 `native_usage` 原始结构。供应商原始统计留在回执里（已递归脱敏），报告只求和归一化的 `input_tokens`/`output_tokens`，并显式给出 `vendor_fields_aggregated: false`。这样"来源明确"与"不泄漏"同时成立：任何报告字段都能回答"它从哪来"。

## 缺失不是 0

`usage_source` 用四个值区分事实：`upstream_json_usage`（完整读到非流响应且其报了用量）、`upstream_stream_usage`（流式，终态后观测到用量）、`not_reported`（完整读到响应但它没报用量）、`unobserved`（没读到可判定的响应：取消、超时、失败、断流）。计数用 `missing` 表达缺失，缺失值保持 `null` 且不参与求和；部分报告只记录给出的那一半，另一半留空。0 只在供应商明确给出 0 时记录。这样"未知"不会在报表里变成"零消耗"。

## 请求耗时不是生成耗时

`request_total_ms` 复用回执 `elapsed_ms`：它包含请求读取、上游传输与下游背压，语义上是本次尝试的墙钟总长。首字/首事件延迟另用与尝试同一个单调起点测量，未观察为 `null`。非流请求没有可观测的首事件，因此该字段为 `null` 而非用总长填充。窗口内百分位是精确最近秩，在受限选择集内排序，不扫全表。

## 有界读取

每次报告都是一个明确选择：半开时间窗口（默认 24 小时，上限 366 天）加行数上限（默认 500，上限 5000）与偏移（上限 100000），`offset`/`limit` 直接进入 SQL 的 `LIMIT/OFFSET`。`coverage` 同时给出 `scanned`（本次实际读取的行数）、`matching`（窗口内总匹配数，SQL `COUNT`）、`truncated` 与 `unmetered_total`（旧部署或崩溃遗留的、没有私有度量行的尝试数），因此分页不会伪装成全量。未知参数名、重复参数与非法数字在进 SQL 之前就拒绝。

## 只读 CLI 与迁移归属

迁移属于运行中的服务：启动时若 ledger 已存在且含既有核心表，先整库复制为 `<ledger>.ts043-backup`，再 `CREATE TABLE IF NOT EXISTS` 新表，绝不改既有表结构或行。CLI 只以 `mode=ro` 打开 ledger，缺少私有表时报"尚未迁移"并以退出码 2 结束——它不会为了读一次而迁移或改写文件。身份必须是本部署已注册、仍被授权（native 走发布撤销/过期/权限关系）且凭据仍可解析的注册；没有"全量导出"模式。撤权或凭据失效的注册读不到历史。

## 已知界限与回滚

只证明本地 SQLite 单进程、WAL、可重启核对；不承诺 PostgreSQL 兼容、跨进程原子性、留存期限、容量或高可用。报告不含费用：合同没有 cost 字段，也没有价格登记。回滚：停服务，保留 `<ledger>` 与其 `.ts043-backup` 供核对，切回上一个已审查提交；旧二进制读同一 ledger 时忽略新表，不需要删除它们。不要在真实生产库上删除私有表后重放未知请求。
