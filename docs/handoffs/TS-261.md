## 变更与归属

问题是 Chat 错误分支丢弃全部上游头，Responses 虽保留原错误 JSON 字节，但其 sink 也没有收到等待提示。消费者已有等待恢复规则，本卡只补 Gateway 传递，不新增重试或业务队列。

- 既有 `routing.py` 唯一拥有 `retry_after_headers` 校验。只从上游 HTTP 429/503 的单一 Retry-After 取值；接受 ASCII 非负整数秒，或完整可解析且带显式时区的 HTTP 日期。支持常见 GMT 日期、数字时区及带时区旧式 RFC850 日期；无时区日期不转发。
- 头值最多 128 字符；拒绝重复值、空值、小数、符号、指数、NaN/Infinity、非 ASCII、CR/LF 及其他控制符、错误日期和附带垃圾文本。去除外围空格后透传，不把等待提示换算成另一个值。合法形状仍过现有 `SecretGuard`，数字或日期命中已知凭据也会丢弃。
- Chat 在原有去敏错误响应上只补安全的 Retry-After。原 HTTP 状态、错误正文和终态 receipt 分类保持；503 仍 unknown，429 仍 failed，上游都已经实际开始，不能冒称 not_started。
- Responses `send_responses` 只增加默认 None 的同步 `on_response_headers` sink。Native 调用者用请求局部 dict 接收已过滤头，由原 `start_response(status, content_type)` 装配；原双参数调用者即使收到有效上游提示也继续正常工作。错误体通过原大小、类型、JSON 和秘密检查后才传递提示。
- 成功 JSON/SSE 不附加该头；上游其他头不转发。Native 错误原字节、成功 SSE 原字节、授权、取消、receipt schema、持久账本和单次上游规则未改。没有新运行模块、配置开关、合同、依赖或迁移。
