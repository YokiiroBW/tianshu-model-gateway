### R1 慢磁盘阻塞事件循环 → 磁盘 IO 全部移出事件循环，单写者 + 真实期限

- 缺陷：`sink.py` 的 `_run` 在事件循环任务里同步调用 `_deliver`/`_sync`，`write`/`flush`/`os.fsync`/`close` 都跑在循环线程上；`shutdown` 的 `asyncio.timeout` 无法打断同步 IO，`_flush_and_close` 还在循环上同步 flush/fsync/close。
- 修复：新增**唯一所有者写线程**（`WRITER_NAME = tianshu-log-writer`，daemon）。事件循环只做一件事——在短锁下把行追加到有界交接队列并唤醒写线程；`write`/`flush`/`fsync`/`close`/`_scan_directory` 全部只在该线程执行。`submit_durable` 等待的 future 由写线程在 **flush+fsync 成功之后**通过 `call_soon_threadsafe` 兑现，因此“落盘先于副作用”仍是真 ack，而不是排队即返回。没有用无限 executor 任务替代单写者。
- 真实期限：`shutdown(timeout)` 先置 `_closed`（新工作立即被拒），再用**有界且每步让出**的等待（`JOIN_POLL_SECONDS`）等到期限；期限到点即 `_abandon()`：**绝不**关闭写线程仍持有的句柄、**绝不**把未返回的写判为失败，只把仍在队列/在飞的行以 `False` 回答，使没有调用者悬空。超时后的写不会被取消，也不会重发模型/消息。
- 取消：等待中的调用者被取消只停止等待，记录仍按原序号最多写一次；`_in_flight` 在队列锁内发布、在回答调用者之后才清空，超时路径不可能漏掉“已出队但未回答”的行。
- `probe_write()` / `close_sync()`（`__main__.py` 维护子命令使用）已与新通道对齐：无写线程时（CLI 维护路径）在调用线程同步执行——该线程就是句柄所有者；有写线程时维护动作经队列交给所有者，调用者用线程事件有界等待，**不会**出现第二个写者。

### R2 封段/恢复绕容量 → 全部输出同一套精确预留

- 缺陷：行预算只在一处检查，但轮转时 `_append(seal)` 不检查封段记录字节；恢复路径直接 `_append`，两者都不查目录/段预算。协调者实测 `rotation_capacity budget=67108864 actual_bytes=67109190 excess_bytes=326`、`recovery_capacity budget=33554432 actual_bytes=33554754 still_accepts_new_work=true`。
- 修复：新增 `_plan(line, recovering)` —— **写第一个字节之前**把「行 + 需要的 `log.segment_sealed` + 降级时随行的 `log.recovered`」三者一起，同时对段上限（64 MiB）与目录预算求预留；预留不成立则整条拒绝，一个字节都不写。`log.recovered` 只在它**自己** flush+fsync 成功后才把状态改回 `ok`（“缓冲区写成功”不再算恢复）。
- 拒绝语义不变且更严：不删未采集文件、不削记录、不扩预算；拒绝时状态 `unavailable`、原因 `capacity`（首个原因胜出，后续症状不覆盖）、`accepts_new_work()` 为假（已关闭的汇同样不再接受新工作），就绪 `logging=failed`。
- 对账：`log.segment_sealed` 的序号在触发轮转的那条记录之后分配（那条记录的身份属于调用者），因此文件内序号不保证按行递增；但**每个已分配序号都可对账**——`1..N` 连续存储且无洞，`N+1` 是被拒的记录，`N+2` 是宣告拒绝的应急行（它自带序号，运维可据此把每一个空洞对上原因）。测试逐条断言了这一点。

### R3 非转发成功终态丢关联 → 终态写进关联上下文之内

- 缺陷：`errors` 中间件在 `finally` 里 `reset_correlation(token)`，之后才在 `finally` 之外补记 `request.finished`，于是非转发成功（回执读取、用量报告等）的终态 `correlation_id` 为 `null`。
- 修复：把该终态记账移入 `try/except/else/finally` 的 **`else` 分支**，即“路由正常返回”这一分支内——它仍在关联上下文里，`finally` 之后才释放。转发路径不变（其终态仍由传输路径在请求内记账）。探针路径仍然结构性不记账。

## 风险

1. **非持久降级是显式的、不是生产可接受的**：未配置日志目录时记录只到 stderr 且就绪永远不为 ready。这保证“不把未配置服务显示成成功”，但部署方若忘记挂载卷，业务将被 503 拒绝——这是有意选择，需要部署文档与运维约定配合。
2. **容量故障直接拒绝新业务**：目录预算耗尽时新业务被拒（503），而不是降级为“不记日志继续服务”。选择“宁可拒绝也不无日志转发”是卡内硬要求，但意味着日志卷容量属于可用性关键路径。
3. **关联头传播依赖平台侧配合**：平台生产者若对未知请求头严格校验，可能拒绝内部快照调用；本卡不改平台侧。
4. **就绪的 `platform`/`model` 只在内部有效期内有真实成功观测才为 `ok`**：有效期过短会导致就绪面板频繁回落到 `not_verified`（不影响 Chat 可用性），部署方需要按实际调用频率配置。
5. **Windows 上示例文档的绝对路径规则不可断言**：`config/container.example.json` 用 POSIX 路径，Windows 主机上 `Settings.validate()` 的绝对路径判定不适用，因此该用例按平台跳过；POSIX 上会真实执行校验。
