### 关键正确性断言（不是“脚本跑完”）

- **无采样、schema 验真**：34 条事件逐一编码并校验；未登记的名称/结果/错误码组合被拒；被篡改的合同包、未知版本、被篡改的 `level` 一律拒绝。
- **同一请求唯一终态**：真实请求 + 真实拒绝 + 真实未匹配路由，终态事件数恰等于请求数。
- **落盘先于副作用**：在**上游替身内部**读取已存段，`upstream.call_started` 必须已经在盘上；日志汇不可用时连续三次业务请求全部 503 `dependency_unavailable`，上游调用计数为 0，回执表零行，已存文件逐字节不变，之后真实恢复只允许一次新的上游调用（被拒的尝试不重发）。
- **容量故障不伪造就绪**：真实占满目录预算后状态为 `unavailable`、原因为 `capacity`、就绪 `logging=failed` 且 503；探针连打三次不能恢复；只有维护命令的真实成功写入能恢复。

- **敏感 canary 零泄露**：正文、凭据反射（JSON/SSE/失败响应三路）、异常文本、恶意请求 ID、URL 查询与路径六类 canary，扫描“已存段 + 应急通道 + 应用日志 + 客户端可见响应”四种输出，全部零命中；同时断言扫描非空转（相关事件确实存在）。

## 风险

1. **非持久降级是显式的、不是生产可接受的**：未配置日志目录时记录只到 stderr 且就绪永远不为 ready。这保证“不把未配置服务显示成成功”，但部署方若忘记挂载卷，业务将被 503 拒绝——这是有意选择，需要部署文档与运维约定配合。
2. **容量故障直接拒绝新业务**：目录预算耗尽时新业务被拒（503），而不是降级为“不记日志继续服务”。选择“宁可拒绝也不无日志转发”是卡内硬要求，但意味着日志卷容量属于可用性关键路径。
3. **关联头传播依赖平台侧配合**：平台生产者若对未知请求头严格校验，可能拒绝内部快照调用；本卡不改平台侧。
4. **就绪的 `platform`/`model` 只在内部有效期内有真实成功观测才为 `ok`**：有效期过短会导致就绪面板频繁回落到 `not_verified`（不影响 Chat 可用性），部署方需要按实际调用频率配置。
5. **Windows 上示例文档的绝对路径规则不可断言**：`config/container.example.json` 用 POSIX 路径，Windows 主机上 `Settings.validate()` 的绝对路径判定不适用，因此该用例按平台跳过；POSIX 上会真实执行校验。
