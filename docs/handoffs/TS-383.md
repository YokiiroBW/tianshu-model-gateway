# TS-383：模型配置读取的并发隔离

基线为已上线R7 `29098f060d5055e69b079222d4de4d41c2ed2f42`，独立分支`codex/chain-gateway-20261028`；不写其他产品、依赖锁或共享合同。

## 根因与变化

`ConfigCache.get`与`NativeConfigCache.get`原各有一把全局async锁，覆盖远端snapshot等待。某个版本或native身份的慢源读取会挡住无关配置的缓存命中/读取，发生在模型调度前，无法由已有公平调度解除。

复用配置模块内`VersionLocks`：Chat按确切version串行，native按既有(identity,requested_version)键串行。每键保留真实持有者与排队引用，等待取消不移除仍使用的锁，空闲键立即释放；同键仍共享已核验缓存，不引入新的业务缓存或账本。未指定native版本仍每次向平台查询，不以旧current缓存代替。

撤销在等待前/远端返回后及同版本fallback时照常核验；来源版本、完整合同、身份/namespace、过期、immutable摘要、仅transport outage fallback与返回值deepcopy保持。模型转发、队列、公平、流式和receipt路径未重写。

## 实际验证

- 新5项异步回归覆盖不同版本互不等待、native身份隔离、同键共享/等待取消、读取期间撤销、仅outage复用原缓存；使用冻结合同、真实隔离SQLite Diagnostics和可控来源。
- 同样新回归在精确R7原source执行2节点，3个场景因全局锁超时失败（3.104s），保留`.runtime/ts383-baseline-blocked-r1.log`；不是环境/hash失败。
- 本地集中网关、Chat/Responses HTTP、来源续期、调度、后台、检索/模型执行套件：190节点，178通过、12跳过，40.410s。12项均因未指定TS110_PLATFORM_ROOT而未执行真实产品联合续期；不称190全通过。原日志`.runtime/ts383-suite-r1.log`与摘要`ts383-validation.json`。
- Ruff check/format及diff检查通过。首轮新测试误指当前协调库旧合同导致4个fixture初始化hash失败，改为已冻结R7 verification-r3合同后通过，未改pin或产品来接受旧合同。
