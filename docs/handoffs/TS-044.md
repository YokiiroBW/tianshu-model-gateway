### 1.2 调用端口与状态所有者

| 端口 | 输入（已核验） | 输出 | 状态所有者 |
| --- | --- | --- | --- |
| `BoundedAdmissionScheduler.acquire(service, workload_class, declared_workload, key, provider_id, timeout_ms)` | 已认证主体、部署绑定类别、启动键、**已由固定版本配置选定的 provider**、期限 | `Waiter` 或领域异常 | 调度 |
| `BoundedAdmissionScheduler.release(waiter)` | 已取得的 permit | 无（幂等，唯一权威释放路径） | 调度 |
| `BoundedAdmissionScheduler.record(sink)` / `drain()` / `waiting_overtakes(class)` | 诊断端口、待发事实、只读查询 | 无返回值 / 事实列表 / 计数 | 调度（观测边界） |

| 领域异常 `AdmissionRefused` / `QueueFull`(429) / `DuplicateRequest`(400) | 固定原因串 + HTTP 状态 | server 适配为 `Rejected` | 调度定义、server 映射 |

| `Gateway.requeue_reverify(request, grant, native, provider)` | 等待结束后的请求、授权、协议、provider | 当前上游凭据，或 `Rejected(401/403)` | server（发送前重验） |
| 时钟 | 构造注入（默认 `time.monotonic`） | 单调时间 | 测试可替换 |

provider 只作为 `acquire` 的一个**输入**传入：队列里没有"稍后再选 provider"的阶段，因此等待不可能把请求改投到别的 provider。

## 2. 实际变更

- **新增** `src/tianshu_gateway/scheduler.py`：单进程内存有界准入调度。公开端口 `acquire/release/bind`、领域异常、观测结果常量；只依赖标准库。
  - 容量模型：全局硬上限与每 provider 硬上限独立判定，两个门都满足才发放 permit。
  - 保留容量：后台最多持 `max_in_flight - interactive_reserve`（全局）与 `max_provider_in_flight - interactive_reserve`（每 provider）个槽位，用后台**自身**的账本计数（`_background_active` / `_background_provider_active`）衡量，而不是用总负载——这是本轮修正的一个真实缺陷（用总负载衡量会使后台在交互占满池时连自己的额度也用不到）。
  - 等待：同类 FIFO；两类等待者的服务顺序在每次授予后交替，所以排队中的后台请求最多被超越一次；`asyncio.wait_for(asyncio.shield(...))` 实现期限；期限/取消都先出队再放弃，`_discard()` 负责把"已授予但调用方已离场"的许可归还。
  - 单遍 `_pump_locked`：一次遍历同时尝试两个类别，避免"已批准但尚未挂接 provider 门"造成的死锁。
  - 观测：事实在锁内成形、锁外发送；sink 未装配时是 `_ignore`，装配后由组合根指向私有 ledger。
- **修改** `config.py`：`SchedulingPolicy`（含 `validate()` 与 `default_policy`）与 `Classification`（`for_service`）。
- **修改** `server.py`：设置字段与校验、`Gateway.scheduler/pool_active/class_for/declared_workload/slot`、`_CounterSlot`（旧语义）、两条路由的准入接线与**等待后重读配置 + `requeue_reverify()` 重验身份/凭据**、`record(self.diagnostics.record_admission)` 装配、连接器上限改为 `max(max_concurrent, max_in_flight) + 1`（等待不占用上游连接）。
- **修改** `diagnostics.py`：`admission_metrics` 表 + 迁移编号 2 + `record_admission`/`admission`。
- **修改** `tests/gateway_fixtures.py`：并发挂起与按尝试放行（保留 `release`/`native_release` 单次挂起语义）。
- **修改** `tests/test_usage_report.py`：迁移断言跟事实更新。
- **新增** `tests/test_ts044_scheduling.py`（58 例）：策略校验、调度核心、旧语义保持、真实网关 + 录制上游场景。

### 与设计稿的偏差（已收敛，记录在案）

- 早期设计有 `acquire` + `reserve(provider_id)` 两阶段；实现收敛为 `acquire(..., provider_id, ...)` 单输入，因为两阶段会让"已批准但未挂接 provider 门"的等待者无法被唤醒（真实死锁，已复现并修正）。
- 后台公平性的度量从"总 provider 负载"改为"后台自身账本"，理由见上。
- 诊断端口从构造注入改为 `record(sink)` 事后装配：构造注入会把一个同步 writer 留在锁的范围内，本轮评审要求"锁内不做同步诊断 IO"，因此事实改在锁内成形、锁外发送。

### 本轮（第二轮）按评审修正的四个缺陷

| 评审条目 | 复现（修复前） | 修复 | 复现（修复后，本轮实跑） |
| --- | --- | --- | --- |
| P1 取消落在授予之后时许可/上游额度泄漏 | `CANCEL_ADMIT_RACE 1 {'p': 1} 0` | `_discard(waiter, outcome)` 单一路径：已授予则归还 | `CANCEL_ADMIT_RACE 0 {} 0` |
| P1 后台被持续交互流量饿死 | `BACKGROUND_AFTER_8_RELEASES False 1`（8 次释放后仍未服务） | `_pump_locked` 交替服务两类等待者 | `BACKGROUND_AFTER_8_RELEASES served_at_round=0 bg_done=True class=background bg_claimed=1 waiting=1` |
| P1 排队期间被撤权的身份仍被转发 | `IDENTITY_REVOKED 200 UPSTREAM 4` | 等待后重读配置 + `requeue_reverify()` 重新认证与重解析凭据 | `IDENTITY_REVOKED 401 CODE unauthorized UPSTREAM_BEFORE 3 UPSTREAM_AFTER 3 INFLIGHT 0 WAITING 0` |
| 可观测性 锁内同步诊断 IO | 事实在锁内直接写入诊断端口 | 锁内只成形事实，`flush()` 在锁外发送；失败只记一条无值告警 | 核心用例断言每次 sink 调用时锁均未持有（含期限拒绝路径），50ms 慢 sink 下期限仍准时 |
