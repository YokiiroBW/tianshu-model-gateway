# TS405 Gateway 链路审查及取消清理

基线 `e30c98a1df65808dc88cf6656ee0a75e5a27ef0a`（与R20运行的0f491be仅AGENTS文档不同）。分支 `codex/ts405-gateway-chain-quality-20261029`。未操作生产、其他产品或真实模型。

## 覆盖及取舍

沿 `server` / `native` 注册入口核对 Chat/Responses、配置与scope校验、`slot`/scheduler准入、取消与执行观察、投递结果/未知状态、provider runtime与origin续期、检索模型执行和PG账本适配。普通与原生请求共用容量，生成前重新校验身份/版本，单次上游发送及持久回执继续由原调用方拥有。

确认两处可复现的同源缺陷：

- acquire已登记等待者、随后争用pump锁时取消，只执行flush，尚未进入 `_wait` 的取消清理，留下无人接收的排队项。
- permit.release先设置本地done，等待scheduler锁时被取消，容量未归还，之后再次release已跳过。重复取消可永久占用槽位，最终拖住前台和后台请求。

acquire现在覆盖登记后全部等待阶段；release保留正常直接协程快路，只有取消异常时才建立有强引用的清理任务。取消不会打断原幂等账本回收，清理结束后继续传播取消；不增加槽位/时限、不重发上游、不改SQL或协议。清理用原 `_discard` / `_release_locked`，没有第二本容量账。

根对单容器host、owner线程、LocalExchange/LoopCall/BodyBridge/ResponseBridge、入口代理、探针与分阶段停止一并追踪；当前注册/依赖与回调闭包未发现有完整证据的新冲突，因此没有为风格重写运行器。反复出现的约120秒排空尚未静态确定具体等待方，保留原正常退出及守护保护，不通过强杀、加时限或清除latch伪装优化。

旧counter模式仍服务显式reserve=0配置，HTTP/TLS客户端仍服务独立部署，账本迁移/CLI仍有兼容职责；这些并非可安全删除的废弃路径。本轮未发现新的无调用实现，未进行无依据退役。
